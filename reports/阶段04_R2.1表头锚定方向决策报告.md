# 阶段04：R2 问题复核与 R2.1 表头锚定方向决策报告

## 一、最终判断

用户提出的问题和调整方向总体合理，应当采纳。

当前应立即暂停 R2，不继续调总阈值，也不把 R2 选中轨迹集合推进生产角色分配。下一步应进入 R2.1，但 R2.1 的第一步不是直接写“表头锚定算法”，而是先做 1015/1035 的表头候选与轨迹审计。

建议执行顺序：

```text
R2 结果冻结
    ↓
表头候选/像素/轨迹全链路审计
    ↓
确认表头真实列线证据确实存在
    ↓
R2.1 表头锚定与主体延伸实验
    ↓
外框 / 主体边界 / 列分隔线角色细分
    ↓
用户完整分辨率复核
```

当前不应进入生产角色分配，也不应计算或宣称列数。

## 二、对用户四个问题的回答

### 1. 用户对问题的判断是否合理？

合理，而且与实际 R2 代码和 JSON 输出一致。

#### R2 确实会把内部线误选为绿色结构

当前 R2 的 `separator` 分数仍主要由以下因素构成：

- R1 结构分数；
- 相对长度和覆盖率；
- 左右顺序稳定性；
- 相邻间距；
- 结构族邻居数；
- 局部横向形态学支持。

这些因素回答的是“它是否像一条稳定的纵向轨迹”，并没有直接回答“它是否是表格列线”。只要内部岩层线或水纹足够长、连续、方向稳定，就可能进入绿色选中集合。

#### R2 确实会遗漏真实列线

R2 的输入仍然是上一阶段已经形成的软轨迹。若真实列线在以下任一环节没有形成轨迹：

1. 候选检测；
2. 候选局部方向提取；
3. 软轮廓整合；
4. R1 轨迹生成；

R2 只能看到剩余轨迹，无法凭空恢复它。

此外，R2 的全局筛选阈值可能把真实列线和内部线一起排除，尤其是出现以下情况时：

- 表头线较短；
- 表头线在主体中间有缺口；
- 表头线与相邻线距离异常；
- 真实列线只在局部主体区域出现；
- 真实列线的整体方向被文字或其他线段污染。

#### 蓝色 `table_boundary` 不稳定是实际设计缺陷

当前代码中 `table_boundary` 只是一个与 `frame`、`separator` 并列的分数项，并不是由明确的主体边界拓扑产生。

当前角色分配大致是：

```text
最高角色分数 → 临时角色
选中集合最外侧轨迹 → 可能改成 frame
中间位置且此前为 frame → 可能改成 table_boundary
```

这会导致：

- `table_boundary` 没有稳定的定义；
- 外缘位置被错误地当成 frame；
- 主体边界没有独立的横线端接或包围证据；
- 蓝色线可能完全不出现，或者随阈值变化而变化。

#### R2 选中集合不能作为最终列结构

这一判断必须保留。当前 R2 输出中的：

```text
selected_by_global_structure = True
```

只表示“通过当前实验的全局结构筛选”，不表示：

- 已经确认是表格列线；
- 已经区分了 frame/table_boundary/separator；
- 已经得到真实列数；
- 已经排除了所有水纹、岩层线和文字。

## 三、对用户建议的采纳情况

### 建议一：暂停当前 R2

采纳。

R2 已经完成了一个必要的探索：证明仅靠长度、连续性、竖直性、顺序和间距不能可靠完成角色判断。继续微调总阈值只会在“漏线”和“误吸内部线”之间移动，不能解决信息缺失问题。

### 建议二：先做表头候选和轨迹审计

完全采纳，并且这是 R2.1 的必要前置步骤。

必须从实际数据建立以下审计表：

| 字段 | 内容 |
|---|---|
| image | 1015 或 1035 |
| header_candidate_id | 表头区域对应候选 ID |
| label | 原始 label，保持不修改 |
| direction | 原始 direction，保持不修改 |
| length / bbox | 实际候选属性 |
| local_vertical_evidence | 表头局部纵向证据 |
| binary_support | 二值图像素支持 |
| skeleton_support | 骨架坐标/细化支持 |
| soft_track_id | 是否进入上一阶段软轨迹 |
| R1_status | R1 中的轨迹与分数 |
| R2_status | R2 是否选中或拒绝 |
| loss_stage | 首次消失环节 |
| ambiguity | 是否与相邻线无法区分 |

这张表必须来自实际候选 JSON、骨架坐标和当前 R1/R2 JSON，不能从视觉印象或历史报告反推。

### 建议三：改为表头锚定的 R2.1

采纳，但需要将“表头锚定”定义为软锚定，而不是硬直线延伸。

表头锚定应当提供：

- 左右顺序锚点；
- 轨迹起始位置锚点；
- 表头局部方向锚点；
- 表头像素支持锚点；
- 多条列线之间的相互间距锚点。

它不能强制：

- 每条表头线贯穿整张图；
- 每条表头线只有一个主体延伸；
- 表头和主体之间没有缺口；
- 所有表头线都属于主体列分隔线。

### 建议四：外框、主体边界和列分隔线在表头锚定后再细分

采纳。

正确顺序应是：

```text
先找有表头证据支持的纵向结构族
→ 再向主体延伸
→ 再利用横线端接和包围关系细分角色
```

而不是：

```text
先对所有轨迹直接打 frame/boundary/separator 分数
→ 再从最高分猜角色
```

## 四、必须补充的内容

用户建议已经抓住主方向，但还需要补充以下五点。

### 1. 必须审计“候选不存在”和“轨迹丢失”两类情况

表头审计不能只看 R2 是否拒绝。必须区分：

```text
A. 表头像素存在，候选也存在，但没有进入软轨迹
B. 表头候选进入软轨迹，但被 R1/R2 排除
C. 表头候选和软轨迹都存在，但被错误轨迹抢占
D. 表头像素存在，但候选检测阶段根本没有候选
E. 表头区域本身无法区分真实列线和文字/内部线
```

只有 A～D 可以通过算法链路修复；E 必须停止并请求人工确认。

### 2. 表头可能有多层，不能只定义一个 header band

1015/1035 的表头可能包含：

- 多层文字标题；
- 多条横向分割线；
- 合并表头区域；
- 只在表头出现的辅助线；
- 主体列线从表头下方才开始的情况。

因此 R2.1 应输出多个候选表头结构层，不能把整张图顶部固定若干百分比区域硬编码为唯一表头。

### 3. 需要维护左右顺序的“锚点到主体”对应关系

不能只对每条表头线单独向下追踪。需要联合约束：

- 表头锚点的左右顺序；
- 主体延伸后的左右顺序；
- 锚点之间的间距变化；
- 两条延伸轨迹不能交叉；
- 同一候选不能同时服务于两个表头锚点；
- 一个表头锚点可以保留多个主体延伸假设，直到后续证据区分。

这应该采用有向候选图、动态规划或小规模非交叉路径选择，而不是重新使用硬 Union-Find。

### 4. 需要将“表头支持”与“主体连续性”分开计分

建议至少保留三个独立分数：

```text
header_anchor_score
body_continuation_score
global_correspondence_score
```

这样可以区分：

- 表头很强但主体缺失；
- 表头较弱但主体长而稳定；
- 表头和主体都支持且顺序一致；
- 只有主体长、没有表头支持的内部线。

最后一类不能因为长度高就直接升级为列线。

### 5. 需要保留 top-k 延伸假设和不确定状态

对于表头锚点无法唯一延伸到主体的情况，不能立即选择最长轨迹。应保留少量 top-k 候选，并记录：

- 连接得分；
- 缺口；
- 横向残差；
- 曲率变化；
- 是否与相邻锚点冲突；
- 是否跨越或跳到岩层线。

只有在全局结构中胜出后，才进入选中结构；无法区分的继续保持 `uncertain`。

## 五、R2.1 建议执行方案

### R2.1-A：表头候选与像素审计

只读处理 1015 和 1035。

输出：

- 表头局部候选审计 JSON；
- 表头候选 ID 标注图；
- 候选到软轨迹的成员映射；
- 候选首次消失环节；
- 二值/骨架支持核查；
- 与相邻线的歧义说明。

这一阶段不改变算法，不改变 label，不恢复主体轨迹。

停止条件：

- 表头真实像素不存在；
- 候选 JSON 和骨架证据均不存在；
- 无法区分真实表头列线与相邻内部线。

### R2.1-B：表头锚点生成

从全部候选局部证据中生成表头锚点：

- 使用局部切向，而非整条 polyline 的全局 direction；
- 使用表头像素支持；
- 使用表头横线交点和端接；
- 维护左右顺序；
- 不把锚点直接升级成主体列线。

### R2.1-C：锚点到主体的延伸图

每个锚点向主体区域建立候选延伸图。边分数包括：

- 局部方向连续；
- y 缺口；
- x 残差；
- 局部曲率；
- 像素支持；
- 与相邻轨迹的顺序关系；
- 与横向表格结构的交点；
- 是否跳到岩层/水纹轨迹。

联合选择时加入：

- 不交叉；
- 左右顺序稳定；
- 锚点与主体一一对应或明确标记多对一歧义；
- 不能重复占用互斥候选片段。

### R2.1-D：角色细分

只有完成锚定和主体延伸后，才细分：

- `frame`：外缘包围、端接闭合或外框关系充分；
- `table_boundary`：主体表格区域边界、与横向主体结构有稳定端接；
- `separator`：位于主体内部、与表头锚点及相邻列关系一致；
- `internal_or_noise`：没有锚点支持或主体对应关系不成立；
- `uncertain`：证据冲突或多个延伸假设接近。

## 六、R2.1 验收标准

### 必须逐条回答

对于每一条用户认为是真实的表头列线，必须能回答：

1. 表头候选 ID 是什么；
2. 它是否有二值和骨架像素支持；
3. 它是否进入软轨迹；
4. 如果没有进入，第一次在哪个环节消失；
5. 如果进入，R2.1 是否找到主体延伸；
6. 如果没有延伸，具体被哪个关系条件拒绝；
7. 它最终属于 frame、table_boundary、separator 还是 uncertain。

### 图像验收

必须输出：

- 表头候选 ID 标注图；
- 表头锚点图；
- 锚点到主体延伸图；
- 选中结构完整分辨率图；
- 被拒绝/不确定结构图；
- 1015 和 1035 的逐轨迹 JSON。

### 禁止事项

- 不为 1015/1035 写坐标特判；
- 不把表头锚点硬延长成直线；
- 不用固定列数；
- 不用用户估计的列数作为真值；
- 不把所有表头竖线直接当成 separator；
- 不为了恢复表头而重新吸收大量内部线和水纹；
- 不进入生产角色分配，直到用户查看完整分辨率图。

## 七、是否需要继续加入长度对比、表头分析等维度

### 长度对比

需要加入，但只能作为辅助维度：

- 归一化长度；
- 分层覆盖率；
- 共同覆盖高度；
- 表头至主体的持续性。

不能把长度作为真实列线的充分条件。

### 表头分析

必须加入，并且应当成为 R2.1 的主锚点之一。

但第一版不需要 OCR。优先使用：

- 表头局部纵向像素支持；
- 表头横线交点；
- 表头多线左右顺序；
- 表头到主体的延伸一致性；
- 表头候选的候选 ID 和骨架证据。

## 八、最终决策

用户提出的方向应当采纳，并作为下一阶段正式工作顺序：

```text
暂停当前 R2
→ 先做表头候选/轨迹审计
→ 确认真实表头证据和首次消失环节
→ 实现 R2.1 表头软锚定与主体延伸
→ 再细分 frame / table_boundary / separator
```

当前只完成方向决策和范围定义，没有修改代码、没有重新运行实验、没有进入生产角色分配。
